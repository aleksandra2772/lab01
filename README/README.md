# Анализ информационной системы
## 1. Описание системы

Название: GitHub

Ссылка: https://github.com/

Назначение:
GitHub - платформа для создания программного обеспечения. Она позволяет разработчикам хранить проекты в репозиториях, отслеживать изменения в коде и работать над ним в команде.

Целевая аудитория:
- Программисты и разработчики
- Студенты и преподаватели, изучающие программирование
- Команды и компании, ведущие совместную разработку
- Авторы проектов с открытым исходным кодом
- Специалисты по тестированию и администрированию (DevOps QA-инженеры)

Основные возможности:
- Хранение проектов в репозиториях
- Контроль версий на основе системы Git
- Совместная работа над кодом
- Отслеживание задач и ошибок
- Предложение изменений в проект
- Публикация и демонстрация проектов
- Управление доступом к проектам и командам
- Автоматизация сборки и проверки кода

Выбранный сценарий:
Создание Git репозитория.
В рамках сценария пользователь авторизуется на сайте, нажимает кнопку создания репозитория, вводит его название, настройки и подтверждает создание.

1. Открыть сайт GitHub
2. Выполнить авторизацию в аккаунте
3. Открыть главную страницу пользователя 
4. Нажать в верхней панели меню +
5. Выбрать пункт «New repository»
6. Ввести название репозитория lab01 в поле «Repository name».
7. Ввести описание ITD-21 в поле «Description».
8. Выбрать видимость «Public» в списке «Choose visibility».
9. Оставить параметры «Add README», «Add .gitignore» и «Add license» отключёнными.
10. Нажать кнопку «Create repository».
11. Проверить, что открылась страница созданного репозитория.

В результате выполнения сценария был создан новый публичный репозиторий lab01.

## 4. Анализ серверной части и API

### 4.1. Серверная часть

Серверная часть GitHub отвечает за операции, которые требуют обработки и хранения данных, проверки прав доступа и безопасности. Эти операции нельзя выполнять только в браузере.

В рамках выбранного сценария «Создание нового репозитория» можно предположить выполнение следующих операций на сервере:

- получение и проверка данных формы создания репозитория;
- проверка сессии и прав авторизованного пользователя;
- проверка корректности и уникальности названия репозитория (на это указывают запросы check-name, часть которых завершилась статусом 422);
- создание записи о новом репозитории;
- создание хранилища для файлов и истории изменений проекта;
- формирование ответа клиентской части.

Точная внутренняя реализация серверной части недоступна пользователю, поэтому часть выводов основана на анализе сетевых запросов и поведении системы.

Таблица серверных компонентов:

| Компонент | Предполагаемая роль |
|----------------------|-------------------------------------------------------------------------|
| API | Приём запросов клиентской части (например, POST /repositories) и отправка ответов |
| Бизнес-логика | Проверка сессии и прав, проверка названия, создание репозитория |
| База данных | Хранение пользователей, репозиториев, прав доступа и настроек |
| Файловое хранилище | Хранение файлов проектов и истории изменений |
| Хранилище ресурсов | Хранение статических файлов интерфейса (JavaScript, CSS, изображения) |

### 4.2. Передаваемые данные

При создании репозитория между браузером и сервером передаются данные формы и служебная информация.

В зависимости от выполняемого действия это могут быть:

- владелец репозитория (Owner);
- название репозитория (Repository name);
- описание репозитория (Description);
- параметр видимости (Public или Private);
- параметры добавления README, .gitignore и лицензии;
- служебные данные безопасности и данные сессии пользователя.

Например, при проверке названия клиентская часть передаёт серверу введённое имя и получает ответ о том, можно ли его использовать. При создании репозитория серверу передаются все параметры формы целиком.

Часть этих данных может передаваться в параметрах URL, заголовках или теле HTTP-запроса. Значения служебных данных в отчёте не приводятся.

### 4.3. API и сетевое взаимодействие

В разделе Network были обнаружены запросы типа Fetch/XHR. Они используются клиентской частью для обмена данными с сервером без перезагрузки страницы.

Обнаруженные запросы, связанные с созданием репозитория:

- check-name — проверка названия (статусы 200 и 422);
- check-proposed-repository — проверка предложенного названия (статус 200);
- repositories — основной запрос создания репозитория.

Пример основного запроса:

| Параметр | Значение |
|------------|-----------------------------------------------------------------------|
| Метод | POST |
| Тип | Fetch/XHR |
| URL | https://github.com/repositories |
| Статус | 200 OK |
| Назначение | Передача данных формы создания репозитория на сервер |
| Данные | Название, описание, видимость репозитория и служебные данные безопасности |

В ходе анализа сетевых запросов создавался тестовый репозиторий lab01.1.

API позволяет клиентской части отправлять данные на сервер и получать результат обработки.

| github.githubassets.com | Загрузка ресурсов интерфейса (JavaScript, CSS) |
| avatars.githubusercontent.com | Загрузка аватаров и изображений |

Также обнаружены запросы collect, stats и rum?…, отправляемые скриптами аналитики и мониторинга. Предположительно, они используются для сбора статистики использования и контроля работы интерфейса.

Если назначение домена точно определить невозможно, это указано в отчёте как предположение.

### 4.5. Хранилища данных

Внутренние хранилища GitHub непосредственно из браузера не видны.

Однако по функциям системы можно предположить наличие нескольких типов хранилищ:

| Хранилище | Предполагаемое назначение |
|----------------------|-------------------------------------------------------------------|
| Хранилище ресурсов | Хранение статических файлов интерфейса (HTML, CSS, JavaScript) |
| База данных | Хранение пользователей, репозиториев, прав доступа и настроек |
| Файловое хранилище | Хранение файлов проектов, истории изменений и загруженных файлов |

Эти предположения основаны на функциональности системы. Точная технология хранения данных в рамках анализа не определяется.

![Схема взаимодействия](../images/screenshots/step4-01.png)

Пользователь открывает страницу в браузере, интерфейс (HTML/CSS) и клиентская часть (JavaScript) загружаются из хранилища ресурсов. При подтверждении формы клиентская часть отправляет запрос POST /repositories в API, бизнес-логика обрабатывает его и обращается к базе данных и файловому хранилищу. ## 5. Описание пользовательского сценария

### 5.1. Выбранный сценарий

Название сценария: создание нового репозитория на GitHub.

Цель сценария: создать новый репозиторий для хранения проекта.

### 5.2. Последовательность выполнения сценария

#### Этап 1. Пользователь открывает страницу

Пользователь авторизуется на GitHub и открывает страницу создания репозитория через меню «+» → «New repository» (адрес github.com/new).

На этом этапе браузер загружает необходимые HTML-, CSS- и JavaScript-ресурсы.

#### Этап 2. Пользователь заполняет форму

Пользователь вводит название репозитория, описание и выбирает видимость.

JavaScript обрабатывает ввод и отправляет серверу вспомогательные запросы check-name, на основании ответов интерфейс сообщает, свободно ли выбранное имя.

#### Этап 3. Пользователь подтверждает создание

Пользователь нажимает кнопку «Create repository».

Клиентская часть собирает введённые данные формы и подготавливает их для отправки на сервер.

#### Этап 4. Клиентская часть взаимодействует с сервером

Браузер отправляет запрос POST https://github.com/repositories (тип Fetch/XHR) через API.

В запросе передаются название репозитория, описание, параметры видимости и служебные данные безопасности.

#### Этап 5. Сервер обрабатывает запрос

Сервер принимает запрос и выполняет необходимые операции.

Предположительно, сервер проверяет сессию и права пользователя, корректность и уникальность названия репозитория.

Если проверки пройдены, данные записываются в соответствующие хранилища: создаётся запись о репозитории и хранилище для файлов проекта.

#### Этап 6. Сервер возвращает результат

После обработки сервер возвращает клиентской части ответ со статусом 200 OK.

Клиентская часть получает необходимые данные и открывает страницу созданного репозитория.

#### Этап 7. Интерфейс отображает результат

JavaScript обрабатывает полученный результат и обновляет интерфейс.

Пользователь видит страницу созданного репозитория и результат своего действия.

## 6. Построение архитектурной схемы

### 6.1. Архитектурная схема

Для демонстрационного варианта была построена упрощённая архитектурная схема информационной системы GitHub в сценарии создания репозитория.

На схеме представлены основные компоненты:

- пользователь;
- браузер;
- пользовательский интерфейс;
- клиентская часть (JavaScript);
- API;
- серверная часть (бизнес-логика);
- хранилище данных;
- внешние сервисы.

Пунктирная линия разделяет клиентскую и серверную части системы. Схема показывает направление взаимодействия между компонентами при выполнении сценария.

### 6.2. Взаимодействие компонентов

Основные взаимодействия в системе:

1. Пользователь выполняет действия в интерфейсе GitHub.
2. Браузер отображает интерфейс и выполняет клиентский код.
3. Клиентская часть обрабатывает действия пользователя.
4. При необходимости клиентская часть отправляет HTTP-запрос через API.
5. Серверная часть (бизнес-логика) обрабатывает полученный запрос.
6. Сервер обращается к хранилищу данных.
7. Сервер возвращает результат клиентской части.
8. Клиентская часть обновляет интерфейс.
9. Пользователь видит результат выполненного действия.

Дополнительно серверная часть может взаимодействовать с внешними сервисами, необходимыми для работы системы.
